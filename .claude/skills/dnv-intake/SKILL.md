# dnv-intake — интервью → профиль кейса

Ты ведёшь дружелюбное структурированное интервью и собираешь профиль кейса в
`user/case-profile.json` — **единый источник правды** для всего пайплайна.

## Предусловия (precondition-гард)

Это первый шаг — внешних предусловий нет. Если `user/case-profile.json` уже
существует: спроси, продолжить редактирование или начать заново (не затирай
молча).

## КРИТИЧНО — приватность

- Пиши значения **только** в `user/case-profile.json` (gitignored).
- **НИКОГДА не записывай значения профиля** (имя, NIE, паспорт, доход, адрес) в
  `CLAUDE.md`, в память, в `*.example` или в любой коммитимый файл. Субагенты
  авто-подгружают `CLAUDE.md` — это сломало бы изоляцию field-QA.
- Не проси и не храни то, что не нужно (дата-минимизация).

## Шаг 1. Архетип-гейт

Спроси про форму занятости и семью. **v1 покрывает только:** основной заявитель
= autónomo / независимый контрактор (por cuenta propia, удалённая работа на
иностранного работодателя/заказчика) + опционально **cónyuge** (или pareja) как
зависимый член семьи.

Если кейс иной (наёмный por cuenta ajena, заявитель без этого основания, дети
как основные, и т.п.) — **прямо скажи, что это вне v1**, поставь
`case.archetype_ok=false`, объясни, что движок заточен под другой архетип, и не
подгоняй кейс. Можно собрать профиль частично, но пометь ограничение.

## Шаг 2. Ветвление initial vs renovación

Спроси `case.process_type`:
- **renovación** — дополнительно спрашивай: `applicant.tie_expiry` (для
  арифметики окна подачи), `applicant.first_approval_date`, и — если подаётся
  член семьи — что `family.titular_regage` заполняется **после** подачи titular
  (не выдумывать сейчас).
- **initial** — НЕ спрашивай tie_expiry/first_approval_date (их ещё нет).

Выведи `applicant.tipo_solicitud` (`RENOVADA` для renovación, `INICIAL` для
initial); аналогично `family.tipo_solicitud`.

## Шаг 3. Сбор полей по схеме

Веди интервью по `profile.schema.json` (рядом с этим файлом). Для каждого
`required` поля соответствующей ветки задай вопрос (используй `label`). Правила:

- **Контролируемые словари** (`domain`): принимай только допустимые значения.
  Особенно `applicant.sexo`/`family.sexo` ∈ {**Hombre**, **Mujer**} — не
  оставляй пустым и не пиши «indefinido» (это была реальная ошибка).
- **Производные** (`derived=true`) — вычисляй, не спрашивай (full_name из
  имени+фамилий; tipo_solicitud из process_type; суммы tasa — позже, live).
- Группируй вопросы по блокам (заявитель → работа/доход → семья → даты), не
  заваливай всё сразу. Подтверждай написание имён/NIE (как в паспорте).
- Если значение неизвестно — оставь `null` и пометь; не выдумывай.

## Шаг 4. Запись профиля

Собери `user/case-profile.json` по namespace схемы (плоские dotted-ключи или
вложенный объект — придерживайся одного; рекомендуется вложенный
`{applicant:{...}, work:{...}, family:{...}, case:{...}, tasa:{...}}`,
эквивалентный dotted-ключам схемы).

Провалидируй: все `required` поля активной ветки заполнены или явно `null` с
пометкой; значения доменных полей — из словаря. Сообщи пользователю сводку
(БЕЗ дублирования чувствительных значений в постоянные файлы).

## Шаг 5. Инициализация состояния

Создай/обнови `user/pipeline-state.json` (форма — `user/pipeline-state.json.example`;
контракт + граф предусловий — `user/pipeline-state.schema.md`): проставь
`steps["dnv-intake"] = {status:"completed", last_run:"<сегодня>",
output:"user/case-profile.json"}`, остальные 7 шагов — `{status:"pending"}`.
`dnv-intake` — **единственный** навык, вправе создать файл состояния с нуля.

## Шаг 6. Экспресс-оценка кейса

Сразу после записи профиля и состояния предложи короткую **предварительную
оценку кейса** (пользователь может отказаться). Если согласен — сверь профиль с
`knowledge_base/norms/` и выдай 10–15 строк:

- **Сильные стороны** — что в профиле уже выглядит соответствующим требованиям
  (доход против порога `umbral-ingresos.md`, окно подачи против
  `plazos-silencio.md`, архетип, комплектность ключевых полей).
- **Красные флаги** — что может стать проблемой (доход ниже/впритык к порогу,
  окно подачи упущено/далеко, `null`-поля в обязательных, `archetype_ok=false`,
  известные риск-паттерны из базы).

Обязательная пометка в конце: **«Это предварительная оценка по курируемой базе
(as-of её файлов), до живой проверки `/dnv-research` и `/dnv-verify`; не
юридическая консультация.»** Пороги из базы не выдавай за актуальные — у них
есть as-of, живые цифры даст research.

## Выход

- `user/case-profile.json` — профиль, проходящий схему, достаточный для
  `dnv-documents` без пробелов (на синтетике — без `[ТРЕБУЕТСЯ]` в обязательных).
- `user/pipeline-state.json` — инициализирован.
- Экспресс-оценка (если пользователь согласился) — в чат, с пометкой о
  предварительности.
- Подскажи следующий шаг: `dnv-research` (или сразу `dnv-documents` для тонкого
  MVP-среза). Посмотреть, где вы в пайплайне, можно в любой момент:
  `/dnv-status`.

## Проверка целостности namespace

Профиль и реестр форм делят один namespace. Если меняешь ключи — прогони
`python engine/scripts/check_namespace.py` (registry ⊆ schema).
