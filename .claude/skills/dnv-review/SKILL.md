# Ревью пакета — многоуровневая методология

Когда нужно проверить черновики из `user/drafts/`, используй три независимых
слоя. Вывод — для **черновика, требующего экспертной/официальной проверки**.

## Слой 0. Криптографическая целостность PDF (обязательно)

Этот слой выполняется **при любой проверке PDF-документов**, а не только при
финальном ревью пакета. Особенно проверяй документы, заявленные как
электронно подписанные: `traducción jurada`, справки госорганов, договоры,
письма работодателя и нотариальные документы.

Перед проверкой сообщи пользователю: «Проверяю, действительно ли файл содержит
встроенную CAdES/PAdES-подпись переводчика и сохранилась ли криптографическая
целостность после любых операций с файлом».

### 0.1. Не доверяй видимому оформлению

Изображение подписи, штамп, подпись из macOS Preview, текст `Firmado por...` и
поле `/FT /Sig` сами по себе **не доказывают наличие криптографической подписи**.
Проверь структуру PDF:

- у поля подписи есть непустое `/V`;
- словарь подписи содержит `/ByteRange` и `/Contents`;
- `/SubFilter` соответствует формату подписи (например,
  `/ETSI.CAdES.detached` или `/adbe.pkcs7.detached`);
- подпись не является только визуальной аннотацией вроде
  `/AAPL:isSignatureMarker`.

Если этих признаков нет, прямо различай:

- скан документа с рукописной подписью;
- визуально подписанный PDF без криптографии;
- PDF со встроенной криптографической подписью.

### 0.2. Проверь подпись, а не только её наличие

1. Проверь CMS/PAdES валидатором (`pdfsig`, VALIDe) либо извлеки подписанные
   диапазоны из `/ByteRange` и проверь `/Contents` командой
   `openssl cms -verify`.
2. Убедись, что подписанные диапазоны соответствуют текущим байтам файла. Для
   единственной финальной подписи конец последнего диапазона должен совпадать
   с размером файла. Если после подписи есть инкрементальные изменения или
   дополнительные подписи, проверь каждую ревизию и явно опиши их.
3. Зафиксируй `/SubFilter`, алгоритм хеширования, имя подписанта, издателя и
   срок действия сертификата на дату подписания.
4. Разделяй два вывода: **криптографическая целостность** и **доверие к
   сертификату**. Успешная CMS-проверка доказывает неизменность подписанных
   байтов, но без проверки цепочки и отзыва не доказывает действительность
   сертификата или полномочия подписанта.
5. Для электронной `traducción jurada` дополнительно проверь, что подпись
   охватывает весь полученный от переводчика комплект, а не только видимую
   страницу сертификации.

### 0.3. Не ломай подписанный оригинал

После подписи нельзя делать `Print → Save as PDF`, экспортировать через Preview
или LibreOffice, объединять, разделять, редактировать, OCR-ить или сжимать файл:
такие операции удаляют либо инвалидируют проверяемую подпись. Переименование
файла без изменения его байтов подпись не ломает. После любой операции с PDF
повтори всю проверку слоя 0.

### 0.4. Обязательный вывод по каждому заявленному подписанному PDF

- встроенная CAdES/PAdES-подпись: **есть / нет**;
- криптографическая проверка: **успешна / неуспешна / не выполнена**;
- подписант, дата, сертификат и `/SubFilter`;
- охватывает ли подпись текущий файл полностью;
- есть ли изменения после подписи;
- что подавать: исходный подписанный файл, бумажный оригинал/скан или запросить
  новый экземпляр.

Никогда не пиши «подпись действительна» только по внешнему виду документа.

Для работы нужны `user/case-profile.json` и `user/drafts/drafts.json`. Если
чего-то не хватает — сгенерируй недостающее (см. навык по заполнению форм)
или сообщи пользователю, чего не хватает.

## Слой 1A. Механический baseline (детерминированный, исчерпывающий)

```
python engine/scripts/field_qa.py user/case-profile.json knowledge_base/forms/registry.json user/drafts/drafts.json --out-dir user/drafts --allowed-root user
```

Гарантии: **вердикт на КАЖДОЕ поле** реестра (count==полей; молчание = бага),
корректность не правдоподобие, контролируемые словари (ловит `sexo=indefinido`),
галлюцинации (профиль пуст, а в черновике значение → WRONG). Отчёт:
`user/drafts/field_qa_report.md`. Ненулевой выход = есть WRONG.

**Читая «Причину»: до `· реестр:` — вывод механики, после — подсказка из
реестра (`common_errors`), то есть контекст, а не находка.** Поэтому
**`MISSING` ≠ автоматически пробел пакета**: у части полей пусто — это
корректное состояние кейса. Канонический случай — `N.I.E.` на **первичной**
подаче: требования предъявить NIE норма не ставит, а подачу подписывает
представитель (**art. 5 Ley 39/2015** — представительство доказывается
`cualquier medio válido en Derecho`; `norms/solicitud-inicial.md` §5). Тогда
**четыре** `MISSING` по N.I.E. (MI-T, MI-F, tasa-790-038,
tasa-790-038-familiar) — не пропуски. В сводке разделяй такие `MISSING` от
настоящих и **не предлагай заполнить**: выдумывать значение нельзя ни в каком
случае.

## Слой 1B. Независимая ре-деривация (two-process)

Механический baseline сравнивает строки. Ре-деривация добавляет смысловой слой
и **доказуемо не видит черновик**:

1. Вызови субагента **field-qa-reviewer**, передав в делегирующем сообщении
   **только** содержимое `user/case-profile.json` и
   `knowledge_base/forms/registry.json`. **Путь черновика НЕ передавай.** Он
   вернёт ожидаемые значения по каждому полю (вслепую) + межполевые замечания.
2. Затем **сам** прочитай `user/drafts/drafts.json` и сдиффай ожидаемые
   значения с фактическими. Расхождение → WRONG/UNCERTAIN.
3. Изоляция проверяема: ожидаемые значения сгенерированы ДО того, как черновик
   попал в контекст диффа. Если field-qa-reviewer запросил черновик — это
   нарушение, переспроси без него.

Сведи baseline (1A) и ре-деривацию (1B): baseline — пол (must-have),
ре-деривация — потолок (ловит правдоподобные).

## Слой 2. Субстантивное ревью «глазами UGE»

Вызови субагента **official-reviewer**: читает `user/spec.md` + `user/drafts/`,
выдаёт субстантивные замечания (основание, порог дохода, закрытие рисков,
полнота, убедительность). Это не юр-вердикт — риски для последующей экспертизы.

## Сводный отчёт

Собери единый отчёт `user/drafts/review_summary.md`:
- field-QA: счётчики OK/WRONG/MISSING/UNCERTAIN + список WRONG/MISSING, где
  `MISSING` разделены на **настоящие пропуски** и **корректные состояния кейса**
  (см. подсказку реестра в «Причине», слой 1A);
- ре-деривация: расхождения и межполевые замечания;
- official: приоритизированные субстантивные замечания.

Явно укажи: это черновик; перед подачей нужна независимая экспертная/официальная
проверка.
