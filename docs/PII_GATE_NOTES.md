# Заметки для U16 (fail-closed PII-гейт) и U18 (форкер-защита)

Обнаружено при дистилляции базы знаний (U5). Учесть при реализации
`engine/scripts/pii_scan.py`.

> ⚠️ **Этот файл — PII-free по построению.** Он описывает *класс* уязвимости
> денилиста абстрактно, **не приводя реальных значений** (иначе сам файл
> провалил бы гейт). Реальные значения живут только в `_pii_denylist.txt`
> (gitignored).

## 1. Склонения кириллических имён обходят substring-денилист

`_pii_denylist.txt` хранит имена в **именительном** падеже. Но в русскоязычных
источниках имя встречается и в косвенных падежах (родительный, дательный и т.д.).
Литеральный substring-скан по имени в именительном падеже **не ловит**
склонённые формы, потому что меняется окончание.

Иллюстрация класса (условная основа `Имярек-`):

| Падеж | Форма | Ловит ли substring `Имярека` (им. п.)? |
|---|---|---|
| Им. | Имярека | да |
| Род. | Имяреки | **нет** (окончание `-ки`, не `-ка`) |
| Дат. | Имяреке | **нет** |

**Митигация в U5:** при копировании публичных транскриптов в
`knowledge_base/sources/` имя консультанта снято во **всех** падежах (проверено
скан на **основу** имени = 0, а не только на именительную форму).

**Требование к U16 (`pii_scan.py`):** для кириллических имён-денилистов —
матчить по **основе + любые падежные окончания** (regex вида `<основа>[а-яё]*`,
регистронезависимо), а не по точной строке. Иначе гейт пропустит склонённую
форму реального PII.

**Требование к денилисту:** хранить **основы** имён (или явно перечислять падежи);
текущий список полных форм для гейта **недостаточен** без основ-паттернов.

## 2. Транслитерации и диакритика

Транслит-варианты имени (латиница с диакритикой и без) уже перечислены в
денилисте, но гейт должен матчить **регистронезависимо и с нормализацией
диакритики** (латинская буква с акутом и без — одно и то же имя).

## 3. Синтетический example/ содержит NIE-образные плейсхолдеры — НЕ false-positive

`example/mvp-case/` (синтетический кейс U19) намеренно содержит **фиктивные**
NIE вида `X9999999R` / `X9999998T` и planted-bug `X9099999R` (заявитель
«Ivan Testovenko», компания «Acme Remote LLC» — всё вымышленное). Реальные NIE
(`Z…`-префикс) в дереве **отсутствуют** (денилист = 0).

**Требование к U16 (`pii_scan.py`):** pattern-скан NIE (`[XYZ]\d{7}[A-Z]`)
**обязан** приложить allowlist для синтетики — либо исключить каталог `example/`
из pattern-проверки, либо держать список known-synthetic значений — иначе гейт
**false-positive'ит** на легитимных примерах и заблокирует публикацию чистого
репо. Денилист реальных значений при этом остаётся жёстким (0). Проверено
полным свипом: единственные NIE-образные токены в дереве — эти 3 фиктивных.

## 4. Гейт обязан сканировать ИСТОРИЮ и метаданные коммитов, не только дерево

Урок независимого PII-аудита (2026-07). Скан **только рабочего дерева**
(`git ls-files`) слеп к двум классам утечки, которые всё равно уезжают в push:

- **Старые версии файлов в истории.** Реальные значения жили в **прежней** версии
  файла (коммит позже переписан), хотя **текущее** дерево было чистым. Значение,
  «удалённое» из дерева, продолжает шипиться через историю.
- **Метаданные коммитов.** Персональная identity (имя + личный email) в полях
  `author`/`committer` части коммитов — это PII, которого **нет ни в одном файле**.

**Требование к U16/U18 (`pii_scan.py` + CI):** гейт обязан проверять
1. **все достижимые blob'ы во всей истории** — `git rev-list --objects --all` →
   `git cat-file` по каждому blob'у (сильнее, чем `log -p`: ловит каждую версию
   каждого файла), а не только `git ls-files`;
2. **метаданные коммитов** — `git log --all --format='%an <%ae> / %cn <%ce>'`,
   уникальные значения обязаны быть только шаблонной identity.

**Митигация уже применённая:** identity репозитория закреплена **локально**
(`git config user.name/user.email` = `DNV Template <noreply@example.com>`), чтобы
будущие коммиты не регрессировали. При первом релизе история была схлопнута в один
чистый root-коммит + `reflog expire` + `gc --prune=now` (старые blob'ы физически
удалены). Гейт должен это состояние **проверять**, а не полагаться на память.

## 5. Структурное правило: контакты в трекаемых файлах — только зарезервированные значения

Урок из аудита: реальный email **третьего лица** (не заявителя) просочился в
тест-фикстуру. First-party денилист его **не ловит по определению** — денилист
перечисляет значения заявителя/семьи, а это постороннее лицо (из чата). Денилист
никогда не сможет перечислить всех третьих лиц.

**Требование к U16 (`pii_scan.py`):** помимо денилиста — **структурное** правило.
Любой `email` / телефон / `@handle` в **трекаемом** файле обязан быть из
зарезервированного диапазона:

- email → RFC 2606: `@example.com` / `@example.org` / `@example.net` / `*.invalid`
  / `*.test`;
- телефон → dummy-диапазон (напр. `+34 600 111 222`);
- всё, что **похоже на реальный контакт** вне этих диапазонов → **FAIL**.

Это ловит PII третьих лиц, которую денилист перечислить не может. Проверено:
единственный реальный email в фикстуре заменён на `someone@example.com`, история
вычищена.
